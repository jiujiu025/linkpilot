# LinkPilot 定制软路由产品设计方案

> 文档状态：V1.0 设计稿
>
> 适用范围：面向直播、跨境办公和多线路网络接入场景的可远程管理专用软路由
>
> 当前阶段：架构设计，不代表任何真实硬件、线路、协议或生产环境已经验证

## 1. 设计思路

本产品不应被设计成普通 OpenWrt 管理页面，也不应只是 PassWall 的重新包装。产品的核心价值是：

```text
客户即插即用
→ 单 SSID 接入
→ 网页认证
→ 按账号或设备分配线路
→ 严格分流和防泄露
→ 本地探针持续诊断
→ 主备线路自动切换
→ 云端远程运维
→ 配置失败自动回滚
```

总体采用“控制面与数据面分离”的原则：

- 数据面在软路由本地完成 DHCP、Wi-Fi、策略路由、代理转发、防火墙和故障切换，不能依赖云端实时转发流量。
- 控制面在云端完成设备、客户、线路、策略、配置版本、探针数据、审计和运维管理。
- Router Agent 主动向云端建立出站加密连接，云端不直接开放软路由管理端口。
- 所有重要配置都经过版本化、校验、签名、原子应用、健康验证和自动回滚。

本设计不承诺绝对零 Bug 或绝对零泄露。产品必须通过真实硬件、真实线路、长时间直播压力、网络故障、安全和恢复测试后，才能进入销售验收。

## 2. 产品定位和边界

### 2.1 产品定位

面向直播和跨境业务场景的品牌化网络接入设备，具备：

- 单 SSID 接入和本地统一登录门户；
- 账号、设备与线路策略绑定；
- 自定义线路和多协议适配；
- 全局代理、严格阻断直连和可配置分流；
- 本地探针、云端探针、故障诊断和主备切换；
- 云端远程授权、配置、回滚、升级和审计；
- 客户只能看到品牌化页面，不能接触底层系统和线路凭证。

### 2.2 明确不做的事情

V1 不做以下内容：

- 不把 OpenWrt LuCI、SSH、Telnet 或 PassWall 原始页面暴露给客户；
- 不允许云端执行任意 Shell 命令；
- 不在客户页面展示 UUID、私钥、完整订阅链接或线路服务端敏感信息；
- 不把云端作为实时数据转发中继；
- 不承诺所有协议、所有终端和所有网络环境都能做到完全无感切线；
- 不设计规避监管、规避安全审查或违反当地法律法规的功能和宣传语；
- 不在没有真实硬件和真实线路验证的情况下宣称可量产或“100%稳定”。

## 3. 用户角色和权限

采用统一登录入口，不让用户选择“普通用户”或“管理员”。账号登录后，由服务端根据权限返回对应功能。

### 3.1 角色

| 角色 | 访问入口 | 权限范围 |
|---|---|---|
| 客户用户 | 软路由本地门户 | 查看自身服务、线路状态、设备状态和基础流量 |
| 设备管理员 | 软路由本地门户 | 管理绑定的单台软路由、Wi-Fi、设备授权和已分配线路 |
| 运营管理员 | 云端运营后台 | 管理授权范围内的客户、设备、线路和工单 |
| 超级管理员 | 云端运营后台 | 管理全部资源、人员、权限、密钥和系统设置 |
| 审计人员 | 云端运营后台 | 只读查看设备、配置、操作和安全审计记录 |
| 线路管理员 | 云端运营后台 | 管理线路、协议配置、健康状态和线路分配 |

### 3.2 权限原则

- 客户账号只能访问自己的设备和被授权的线路。
- 设备管理员只能管理绑定的单台软路由，不能查看其他软路由。
- 云端后台才具备全局设备管理能力。
- 所有 API 必须在服务端执行身份、角色、租户、资源归属和操作状态校验。
- 前端隐藏菜单只是体验措施，不能作为安全边界。
- 高风险操作必须二次确认，并记录操作者、目标、原因、结果和时间。

## 4. 总体架构

```text
                    ┌──────────────────────────┐
                    │      云端运营后台          │
                    │ 客户、设备、线路、探针、审计 │
                    └────────────┬─────────────┘
                                 │ HTTPS / WebSocket
                    ┌────────────▼─────────────┐
                    │      LinkPilot Control    │
                    │ API、Worker、配置、任务、权限 │
                    └────────────┬─────────────┘
                                 │ 主动出站加密连接
                    ┌────────────▼─────────────┐
                    │       Router Agent       │
                    │ 身份、配置、命令、状态上报 │
                    └────────────┬─────────────┘
                                 │ 本地受限接口
        ┌────────────────────────┼────────────────────────┐
        │                        │                        │
┌───────▼───────┐        ┌───────▼───────┐        ┌───────▼───────┐
│ OpenWrt 网络层 │        │ 代理数据平面   │        │ 本地探针/守护 │
│ Wi-Fi、DHCP、  │        │ sing-box、     │        │ 健康检查、    │
│ VLAN、防火墙   │        │ Xray、WireGuard│        │ 回滚和恢复    │
└───────────────┘        └───────────────┘        └───────────────┘
```

### 4.1 控制面

控制面包括：

- 客户和租户管理；
- 软路由设备管理；
- 线路、协议和 RouteProfile 管理；
- 配置版本和 Desired State 管理；
- Worker 异步任务；
- 本地和云端探针数据接收；
- 故障事件、切线记录和审计日志；
- 远程模拟客户门户；
- OTA 固件和 Agent 版本管理。

V1 推荐使用 Modular Monolith + Worker，不因为功能多就直接拆成大量微服务。

### 4.2 数据面

数据面必须在本地完成：

- DHCP、DNS、Wi-Fi 和局域网通信；
- 客户门户的本地认证；
- 设备会话和账号策略绑定；
- TCP、UDP、QUIC 等流量转发；
- TUN/透明代理和策略路由；
- IPv6 防护；
- DNS 防泄露；
- Kill Switch；
- 主备线路探测和切换。

云端不可用时，已经生效的配置、已授权会话和自动切线逻辑仍应在本地继续工作。

## 5. 软路由系统分层

```text
品牌化客户门户
        ↓
本地认证与设备会话层
        ↓
Router Agent
        ↓
策略编译器和本地状态存储
        ↓
nftables / policy routing / DNS
        ↓
sing-box / Xray / WireGuard
        ↓
WAN 线路
```

### 5.1 OpenWrt 基础层

- `netifd`：WAN、LAN、PPPoE、DHCP 和接口状态；
- `hostapd`：单 SSID、WPA2/WPA3 和客户端接入；
- `dnsmasq` 或等效 DNS/DHCP 服务：地址分配和本地解析；
- `nftables`：防火墙、流量标记、Kill Switch 和访问隔离；
- 策略路由：根据设备会话和 RouteProfile 选择线路；
- `procd`：进程守护、启动顺序和异常重启。

### 5.2 代理数据平面

建议优先使用 sing-box，并通过 Xray Adapter 兼容必要的 Xray 配置；WireGuard 作为高性能隧道协议单独管理。

- sing-box：统一管理现代协议、TUN/透明代理、路由和 DNS；
- Xray：兼容现有 Xray 生态中必须支持的协议和配置；
- WireGuard：用于低延迟、高吞吐和稳定隧道；
- 代理核心不直接读取数据库，只读取本地编译后的配置文件或受限运行时接口。

### 5.3 Router Agent

Router Agent 是软路由与云端之间的唯一业务控制入口，负责：

- 设备证书和身份认证；
- 接收签名命令；
- 拉取和验证配置版本；
- 编译本地网络规则；
- 调用受限的本地适配器；
- 上报设备、线路和探针状态；
- 执行配置部署、验证和回滚；
- 执行固定操作，不支持任意命令执行。

Agent 应以最小权限运行，不能拥有不必要的系统管理能力。需要重启网络或服务时，通过本地白名单 Helper 执行固定动作。

## 6. 单 SSID 和本地门户

### 6.1 用户体验

```text
客户连接 LinkPilot-WiFi
        ↓
DHCP 分配局域网 IP
        ↓
未认证设备只能访问本地门户
        ↓
输入账号密码
        ↓
服务端识别账号权限
        ↓
客户或设备管理员进入对应页面
        ↓
设备按账号或设备策略使用线路
```

统一入口不显示用户类型。管理员账号登录后可以看到更多功能，但不能通过页面名称泄露底层 OpenWrt、PassWall、Xray 或 sing-box 信息。

### 6.2 地址设计

本地门户提供：

```text
http://router.local
http://192.168.10.1
```

`router.local` 依赖 mDNS，不能作为唯一入口。固定局域网地址必须始终保留。

本地门户不是 OpenWrt 默认网关管理页，不能提供 LuCI、SSH、Telnet、Shell、原始配置或任意防火墙修改功能。

### 6.3 Captive Portal

建议基于成熟的 `openNDS` 或等效组件实现门户引导，自定义品牌页面和后端认证接口。

未认证设备允许：

- DHCP、ARP、必要的局域网协议；
- 访问本地门户；
- 访问必要的认证服务；
- 访问设备绑定所需的有限本地接口。

未认证设备禁止：

- 访问公网；
- 访问其他客户设备；
- 访问软路由系统管理接口；
- 通过普通 WAN 直连。

不能粗暴劫持所有 HTTPS 请求，否则会造成证书错误。需要利用终端系统连通性检测和 HTTP 门户引导，并保留手动访问地址。

### 6.4 无浏览器设备

编码器、摄像机等设备可能无法打开门户。设备先通过 DHCP 获得 IP，显示为“待授权设备”。客户或设备管理员使用手机、电脑访问本地门户，按以下信息选择设备：

- 设备主机名；
- 局域网 IP；
- MAC 地址后四位或脱敏标识；
- 接入时间；
- 有线 LAN 端口；
- 最近流量和在线状态。

直播设备建议使用网线直连软路由，避免二次 NAT 导致设备无法被准确识别。

## 7. 账号、设备和线路模型

### 7.1 核心关系

```text
Customer
  ↓
PortalAccount
  ↓
DeviceSession / DeviceRouteBinding
  ↓
RouteProfile
  ↓
LineGroup
  ↓
CustomLine / ProtocolProfile
```

客户账号是业务身份，VLESS UUID、WireGuard 私钥和其他线路凭证是基础设施凭证，两者必须分离。

### 7.2 主要实体

| 实体 | 作用 |
|---|---|
| RouterDevice | 一台软路由及其设备身份 |
| DeviceIdentity | 设备证书、公钥、状态和吊销信息 |
| PortalAccount | 客户门户账号，不保存明文密码 |
| DeviceSession | 某个接入设备的认证会话 |
| DeviceRouteBinding | 设备与 RouteProfile 的授权绑定 |
| RouteProfile | 主线路、备用线路和分流策略的组合 |
| LineGroup | 同地区或同用途的线路集合 |
| CustomLine | 单条用户或管理员添加的线路 |
| ProtocolProfile | 协议类型和经过校验的参数 |
| RoutingRule | 域名、IP、端口、设备和账号规则 |
| FailoverPolicy | 失败阈值、恢复阈值、冷却和切换限制 |
| ConfigRevision | 配置版本、摘要、签名和生成来源 |
| Deployment | 配置部署、验证、回滚和结果 |
| ProbeCheck | 一次探针检查及其脱敏结果 |
| Incident | 故障事件和诊断结论 |
| AuditLog | 不可篡改的关键操作记录 |

### 7.3 账号登录线路

手机、电脑或其他终端登录门户后，不直接连接 VLESS，而是建立设备会话：

```text
账号登录
    ↓
设备会话认证
    ↓
查询账号允许的 RouteProfile
    ↓
应用设备级流量标记
    ↓
sing-box / Xray / WireGuard 选择线路
```

支持限制：

- 账号有效期；
- 最大同时在线设备数；
- 流量额度；
- 允许的线路地区；
- 允许的分流模式；
- 设备类型或有线端口；
- 强制下线和远程撤销。

## 8. 自定义线路和协议适配

### 8.1 线路录入

管理员可以添加自定义线路，填写线路名称、地区、用途、主备关系和协议参数。敏感参数只在受保护的管理接口中短暂出现，保存前立即加密。

线路配置必须经过：

```text
输入校验
→ 协议能力检查
→ 参数规范化
→ 凭证加密
→ 生成配置版本
→ 线路探测
→ 允许绑定
```

### 8.2 协议能力矩阵

V1 设计适配层，不把业务模型绑定到某一个代理核心：

| 协议 | 推荐执行器 | V1 建议 |
|---|---|---|
| SOCKS5 | sing-box | 支持 |
| HTTP/HTTPS Proxy | sing-box | 支持 |
| Shadowsocks | sing-box | 支持 |
| VMess | Xray 或 sing-box | 兼容支持 |
| VLESS | Xray 或 sing-box | 优先支持 |
| Trojan | Xray 或 sing-box | 支持 |
| WireGuard | WireGuard | 优先支持 |
| Hysteria2 | sing-box | 设备性能和版本验证后支持 |
| TUIC | sing-box | 设备性能和版本验证后支持 |
| NaiveProxy | 视执行器和 OpenWrt 包支持情况 | 评估后支持 |

PassWall 的协议列表会因版本和底层核心不同而变化，因此不能简单承诺“完全支持 PassWall 所有协议”。产品应显示实际设备、核心版本和硬件能力对应的协议矩阵。

### 8.3 凭证安全

- 数据库存储密文、Nonce、密钥版本和摘要，不保存明文凭证；
- 不在日志、异常追踪、前端响应或下载文件中输出完整凭证；
- 设备和客户尽量使用独立线路凭证；
- 支持凭证轮换、失效和远程吊销；
- 支持短期授权凭证，降低设备被攻破后的影响范围；
- 设备被标记为风险后，停止下发新凭证并进入维护状态。

## 9. 全局代理、分流和防泄露

### 9.1 分流模式

提供三个用户可理解的模式：

1. 严格全局代理：所有允许的公网 TCP/UDP 流量走代理，代理不可用时阻断直连；
2. 大陆直连、其他流量代理：符合大陆域名/IP 规则的流量直连，其余流量走代理；
3. 自定义策略：按设备、账号、域名、IP、端口、协议和线路选择规则。

“全部直连”只提供给管理员诊断或维护使用，默认不对普通客户开放。

### 9.2 规则优先级

建议固定为：

```text
局域网和设备管理例外
→ 强制阻断规则
→ 设备/账号专属规则
→ 管理员自定义规则
→ 白名单直连规则
→ 指定线路规则
→ 大陆直连规则
→ 默认线路
```

规则必须提前编译成本地快速匹配结构，数据包转发路径不能查询数据库。

### 9.3 DNS 处理

- 客户端 UDP/TCP 53 强制接管到软路由 DNS；
- DNS 根据 RouteProfile 和域名规则选择直连解析或代理解析；
- 对 DoT、DoH 和硬编码 DNS 采取阻断、受控放行或策略代理；
- 维护 GeoIP、GeoSite 和自定义域名规则的版本；
- 规则更新失败时保留上一版本；
- DNS 缓存必须按策略隔离，避免跨线路污染。

### 9.4 IPv6

V1 默认关闭 IPv6，并在多个层面验证：

- WAN 不获取 IPv6 地址；
- 关闭 DHCPv6 和 Router Advertisement；
- 禁止 LAN 向客户端下发 IPv6；
- 防火墙拒绝 IPv6 公网转发；
- 启动自检确认客户端没有公网 IPv6；
- 探针定期检测 IPv6 泄露。

后续如支持 IPv6，必须实现完整的 IPv6 TUN/透明代理和同等 Kill Switch，不能仅恢复 IPv6 而没有代理能力。

### 9.5 Kill Switch

采用默认拒绝、白名单放行：

```text
允许 DHCP、ARP、门户、控制通道、代理服务器和已验证的代理流量
阻断所有未进入代理链路的普通 WAN 直连
```

代理核心停止、配置校验失败、线路全部不可用时：

```text
保持局域网和门户可用
→ 阻断公网直连
→ Watchdog 尝试恢复
→ 探针验证成功后恢复放行
```

## 10. 探针和故障诊断

### 10.1 两级探针

本地探针负责客户现场，云端探针负责平台和跨地区观测。两者不互相替代。

本地探针监控：

- CPU、内存、温度、磁盘和系统负载；
- WAN、LAN、PPPoE、网卡和链路状态；
- DHCP、DNS 和门户；
- sing-box、Xray、WireGuard 和 Agent 进程；
- 节点端口、协议握手、代理出口和实际 HTTPS；
- 延迟、丢包、抖动、上传和下载能力。

云端探针监控：

- 设备 Agent 是否在线；
- 控制通道是否正常；
- 线路服务端是否可达；
- 不同地区访问线路的质量；
- DNS 和业务目标可达性；
- 多台设备是否出现相同故障。

### 10.2 诊断层级

```text
设备电源和系统
→ 网卡和 WAN
→ DHCP / DNS
→ 代理进程
→ 节点协议握手
→ 代理出口 IP
→ 业务目标访问
```

示例：

```text
Wi-Fi：正常
软路由：正常
WAN：正常
DNS：正常
代理进程：正常
新加坡节点握手：失败
新加坡备用节点：正常
诊断结论：主线路异常，已切换备用线路
```

### 10.3 健康状态机

```text
HEALTHY
   ↓ 连续失败
DEGRADED
   ↓ 达到失败阈值
FAILED
   ↓ 备用验证成功
SWITCHING
   ↓
ACTIVE_STANDBY
   ↓ 主线路连续稳定
RECOVERY_OBSERVING
   ↓
HEALTHY
```

必须配置：

- Failure Threshold；
- Recovery Threshold；
- Cooldown；
- Hysteresis；
- Max Switch Per Hour；
- Lease Lock；
- Fencing Token；
- 维护模式；
- 手动锁定线路。

线路短暂抖动不能立即切换，避免直播连接频繁重建。

## 11. 直播性能设计

### 11.1 硬件建议

当前首款目标样机为小米 AX3000T。最低硬件档参考图片所示配置：MT7981B 双核 1.3GHz、256MB 内存、128MB Flash、Wi-Fi 6、4 个千兆网口。由于同系列可能存在不同硬件和区域版本，仍必须先确认完整型号、硬件版本、SoC、内存、Flash、无线芯片、分区表和恢复方式，再制作或刷写定制固件。

首款样机验证重点：

```text
设备：小米 AX3000T（具体硬件版本待确认）
最低硬件基线：MT7981B 双核 1.3GHz、256MB 内存、128MB Flash、Wi-Fi 6、4 个千兆网口
系统：确认目标型号的 OpenWrt 支持和恢复路径
无线：验证单 SSID、客户端隔离、随机 MAC 和 Wi-Fi 6 稳定性
资源：验证代理、门户、探针和 Agent 同时运行时的 CPU、内存和 Flash 余量
网络：验证有线、无线、全局代理、UDP/QUIC 和直播上传
```

N100/x86 不再作为首款样机，但可以作为后续高性能对照平台。小米 AX3000T 这类最低配置只能在真实测试通过后承担完整数据面；如果无法满足代理吞吐、内存、散热或恢复要求，应改为无线接入设备，由外置高性能网关承担代理数据面，不能为了适配硬件而降低安全和稳定性要求。

### 11.2 直播流量原则

- 支持 TCP、UDP、QUIC 和长连接；
- 直播设备优先使用有线连接；
- 直播设备可以绑定固定主线路和备用线路；
- 同一连接保持线路粘滞，不做逐数据包负载均衡；
- 探针测速使用独立任务、限频和限速，不能抢占直播上传；
- 不默认启用高消耗 DPI 或逐包详细日志；
- 规则编译后在本地内存中快速执行；
- 云端只下发策略，不进入实时转发路径。

### 11.3 切线限制

主线路完全中断时，已有 TCP/UDP/直播连接可能需要重新建立，这是网络层限制。系统应做到：

- 新连接快速切到备用线路；
- 不因短暂抖动频繁切换；
- 提供平滑切换和立即切换两种操作；
- 立即切换前明确提示可能中断当前直播；
- 记录切换时间、原因和恢复结果。

## 12. 客户门户和管理员后台

### 12.1 客户/设备管理员本地页面

统一登录后按权限显示：

- 当前线路和公网出口 IP；
- 延迟、丢包、上下行速度；
- 设备在线状态和已连接设备；
- Wi-Fi 名称和 Wi-Fi 密码修改；

- 简单故障提示。

客户可以看到当前“公网出口 IP”，但不应看到线路服务器管理地址、完整节点地址、UUID、私钥或完整订阅链接。

### 12.2 云端运营后台

地址与本地门户分离，例如：

```text

```

功能包括：

- 全部软路由总览；
- 客户和账号管理；
- 直播设备远程授权；
- 自定义线路和协议管理；
- RouteProfile 和分流规则；
- 探针、健康、故障和切线历史；
- 配置部署、验证、回滚和 OTA；
- 客户门户模拟会话；
- 审计、操作原因和权限管理。

### 12.3 模拟客户门户

管理员可以在后台选择某台软路由，进入与本地客户页面相同的“客户视图”，用于协助诊断。

禁止保存或读取客户明文密码。正确做法是：

```text
管理员授权
→ 云端生成一次性模拟令牌
→ 令牌绑定管理员和指定软路由
→ Router Agent 验证令牌
→ 建立短期模拟会话
→ 默认只读
→ 所有操作记录审计
```

模拟页面应显示明显的运维提示：当前客户、当前软路由、访问模式、剩余时间。高风险修改需要二次确认。

## 13. 远程命令和配置部署

### 13.1 固定命令模型

禁止任意 Shell 远程执行，仅支持白名单命令：

```text
AUTHORIZE_DEVICE
CHANGE_ROUTE_PROFILE
SWITCH_LINE
REVOKE_DEVICE
RESTART_PROXY
RESTART_NETWORK
ROLLBACK_CONFIG
ROTATE_CREDENTIAL
ENTER_MAINTENANCE
UPGRADE_FIRMWARE
```

每条命令包含：

- 命令 ID；
- 目标设备 ID；
- 目标配置版本；
- 过期时间；
- 一次性随机数；
- 操作者和操作原因；
- 数字签名；
- 幂等键。

### 13.2 Desired State 和 Observed State

```text
云端 Desired State
        ↓
配置编译、校验和签名
        ↓
Router Agent 下载
        ↓
本地校验和原子写入
        ↓
启动或切换代理实例
        ↓
本地 Probe 验证
        ↓
Observed State 上报
        ↓
成功保留，失败回滚
```

软路由至少保留：

- 当前稳定版本；
- 上一个稳定版本；
- 待验证版本。

新配置未通过健康验证前，不能删除上一稳定版本。

## 14. 安全架构

### 14.1 设备安全

- 设备首次激活使用一次性 Enrollment Token；
- 每台设备生成独立身份和证书；
- Token 只保存哈希并设置有效期；
- Agent 与云端使用 TLS，后续升级到 mTLS；
- 支持证书轮换和吊销；
- 设备进入维护模式时停止敏感操作；
- 尽可能使用 Secure Boot、签名固件、只读系统分区和双分区升级。

### 14.2 管理安全

- 云端管理员强制 MFA；
- 密码使用 Argon2id 哈希；
- 会话使用 HttpOnly、Secure、SameSite Cookie；
- 登录、修改配置、线路切换和远程控制全部限流和审计；
- 管理后台使用 CSRF 防护、CORS 白名单和输入校验；
- 客户、设备、线路和组织执行严格租户隔离；
- 管理员模拟客户门户使用短期一次性令牌；
- 不显示或记录完整敏感凭证。

### 14.3 被破解后的影响隔离

如果设备被取得最高权限，不能假设本地配置绝对安全。应通过隔离降低损失：

- 每台设备和客户尽量使用独立线路凭证；
- 凭证支持短期有效和自动轮换；
- 云端可远程吊销设备；
- 风险设备停止获取新配置和凭证；
- 后台不提供批量导出线路密钥；
- 设备只能访问必要的控制面接口；
- 设备被隔离后仍需保留审计和告警能力。

## 15. 数据库设计方向

V1 建议保留以下模块：

```text
租户与身份：Organization、User、Role、Permission、Session
设备：RouterDevice、DeviceIdentity、DeviceSession、DeviceCredential
线路：Provider、Server、CustomLine、ProtocolProfile、LineGroup
策略：RouteProfile、RoutingRule、DomainRule、IpRule、FailoverPolicy
部署：DesiredState、ObservedState、ConfigRevision、Deployment、DeploymentStep
探针：Probe、ProbeCheck、HealthSnapshot、Incident、Alert
任务：Job、JobAttempt、Outbox、DeadLetter
审计：AuditLog、SecurityEvent、CredentialRotation
```

关键字段设计要求：

- 所有业务表包含组织或租户边界；
- 敏感字段区分密文、Nonce、密钥版本和摘要；
- 设备、账号、线路和配置建立唯一约束；
- 绑定和授权建立有效期、状态、版本和撤销时间；
- 高并发分配使用事务、行锁或乐观锁；
- 历史部署、探针和审计记录不可直接覆盖；
- 统计快照与计费账本分离，避免重复计算。

## 19. 分阶段开发计划

### Phase 0：架构和样机验证

交付：总体架构、数据模型、协议矩阵、网络拓扑、威胁模型、测试标准和小米 AX3000 样机方案。

完成条件：设计评审通过，确定第一款目标硬件和第一批真实测试线路。

### Phase 1：软路由基础数据面

实现：OpenWrt 定制基础、单 SSID、DHCP、门户、基础防火墙、IPv6 默认关闭和本地状态页。

完成条件：终端可以接入、获得 IP、访问门户，未认证设备不能访问公网。

### Phase 2：账号和设备授权

实现：统一登录、设备会话、客户/设备管理员角色、待授权设备、设备绑定和有效期。

完成条件：不同账号可以在同一 SSID 下绑定不同设备或线路，权限隔离通过测试。

### Phase 3：代理数据面和分流

实现：sing-box、Xray Adapter、WireGuard、RouteProfile、严格全局代理、DNS 接管、Kill Switch、白名单和大陆直连/其他代理模式。

完成条件：真实线路下完成 TCP/UDP/QUIC、DNS、IPv6 和直连泄露测试。

### Phase 4：Router Agent 和云端管理

实现：设备注册、心跳、加密通道、固定命令、配置版本、Desired/Observed State、远程授权和回滚。

完成条件：不访问客户电脑即可远程授权直播设备，配置失败可以自动恢复稳定版本。

### Phase 5：探针和自动切线

实现：本地/云端探针、诊断树、健康状态机、主备线路、锁、冷却、恢复阈值和切换审计。

完成条件：真实线路故障和抖动测试通过，不出现频繁切线或普通 WAN 泄露。

### Phase 6：品牌化门户和模拟客户视图

实现：正式 UI、客户门户、设备管理员页面、云端运营后台、短期模拟会话和响应式布局。

完成条件：客户看不到底层系统，管理员可以查看单台设备并完成远程诊断。

### Phase 7：量产和 OTA

实现：固件签名、双分区 OTA、失败恢复、设备激活、证书轮换、批量部署和售后诊断包。

完成条件：至少完成一次真实升级、失败回滚、救砖和恢复测试。

## 20. 主要风险和决策点

| 风险 | 影响 | 推荐方案 |
|---|---|---|
| 小米 AX3000 具体硬件版本未知 | 无法确认固件、驱动、分区和性能 | 先确认铭牌和硬件档案，再做原厂备份、恢复验证和适配 |
| Captive Portal 兼容性 | 编码器和 IoT 可能无法弹窗 | 保留固定本地地址和管理员远程授权 |
| 单 SSID 设备识别 | 随机 MAC、二次 NAT 会影响绑定 | 优先有线接入，结合会话、IP、MAC 哈希和端口 |
| 线路频繁抖动 | 直播连接中断 | 失败/恢复阈值、冷却、连接粘滞和备用预检 |
| 云端故障 | 远程控制不可用 | 本地继续运行，缓存已授权状态和策略 |
| 代理核心差异 | PassWall 协议不完全一致 | Protocol Adapter + Capability Matrix |
| 设备被破解 | 线路凭证可能泄露 | 独立凭证、短期授权、轮换、吊销和影响隔离 |
| 规则数量过多 | CPU、内存和延迟上升 | 规则编译、缓存、版本化和数量限制 |
| 用户修改 Wi-Fi | 无线设备短暂断开 | 二次确认，保留有线本地入口和远程恢复 |

- 规则编译器和防泄露链路；

### 必须真实验证

- 目标硬件的代理吞吐和散热；
- 直播长连接、上传、UDP/QUIC 和切线影响；
- IPv6/DNS/普通 WAN 直连泄露；
- 编码器、摄像机和随机 MAC 设备识别；
- 云端断开后的本地持续运行；
- 配置失败回滚和固件升级恢复；
- 目标线路的协议兼容性和稳定性。

### 当前推荐决策

先以小米 AX3000T 完成目标硬件识别、原厂固件备份、可恢复启动和基础数据面验证，再决定是否让它承担完整代理数据面。如果小米 AX3000T 的性能或恢复能力不满足要求，采用“小米 AX3000T 负责 Wi-Fi/接入 + 外置高性能网关负责代理和控制”的双设备方案，不降低直播稳定性和安全边界。
