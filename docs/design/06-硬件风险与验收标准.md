# 硬件风险与真实验收标准

## 1. 首款目标样机：小米 AX3000T

当前首款目标样机确定为“小米 AX3000T”。最低硬件档参考：MT7981B 双核 1.3GHz、256MB 内存、128MB Flash、Wi-Fi 6、4 个千兆网口。AX3000T 仍可能存在不同区域或硬件版本，必须在刷写或开发前确认设备底部铭牌、硬件版本、闪存布局、启动方式和当前固件版本。

必须先建立目标设备档案：

- 完整品牌和型号；
- 硬件版本和区域版本；
- SoC、RAM、Flash、无线芯片和网卡芯片；
- 当前 OpenWrt 支持状态和设备树；
- 是否有串口、TFTP、恢复模式或 U-Boot 救砖路径；
- 分区表、固件大小限制和升级限制；
- 是否支持单 SSID、客户端隔离、VLAN 和稳定的 Wi-Fi 6 驱动。

首款样机的 Phase 1～Phase 5 必须直接在真实小米 AX3000T 上验证，不能用 N100 的结果替代。N100/x86 仅作为后续性能对照平台或云端开发测试平台。

Board Profile 和备份/恢复测试计划见：

- `docs/design/08-小米AX3000T-Board-Profile.md`
- `docs/design/09-AX3000T-备份恢复与真实性能测试计划.md`

## 2. 小米 AX3000T 适配风险

主要风险：

- CPU 加密性能可能无法满足直播全局代理；
- 内存和 Flash 容量可能不足以同时运行门户、代理核心、探针和 Agent；
- Wi-Fi 6 驱动、单 SSID、随机 MAC 和多终端稳定性；
- 当前型号的 OpenWrt 支持成熟度、无线驱动和升级路径；
- 双分区、救砖和断电恢复能力；
- 代理核心、规则数量、探针任务和门户造成资源竞争；
- 长时间直播上传时温度、降频、无线驱动异常和 Flash 磨损。

推荐决策：先确认小米 AX3000T 的具体硬件版本并完成最小可启动、可恢复验证，再决定完整系统是否直接运行在该设备上。256MB 内存和 128MB Flash 对精简版数据面属于“条件可行”，不是“已确认足够”；必须实测门户、单一代理核心、Agent、低频探针、DNS 防泄露和 Kill Switch 同时运行时的资源余量。若代理吞吐、内存、散热或恢复能力不达标，应将小米 AX3000T 定位为无线接入设备，并由外置高性能网关承担代理数据面，不应强行把完整系统塞入低配硬件。

基础版不得通过关闭 Kill Switch、DNS/IPv6 防泄露、设备隔离、签名校验、权限校验或回滚保护来适配资源限制。推荐只运行一个代理核心，限制规则、日志、探针测速、协议包和本地历史数据规模。

## 3. 真实性能验收

必须使用目标硬件、目标线路、真实代理配置和真实直播设备。禁止用 mock、假探针、合成成功日志或单纯局域网测速代替真实验证。

至少记录：

- 直连与代理 TCP/UDP/QUIC 吞吐、CPU、内存、温度和抖动；
- 持续上传直播期间的丢包、RTT、抖动、重传和连接中断；
- 单设备、多个直播设备和混合上下行并发；
- 探针运行前后的直播带宽、CPU 和温度变化；
- 主线路中断到备用线路可用于新连接的时间；
- 云端断开后的本地持续运行时间；
- 配置失败回滚时间、重启恢复时间和 OTA 恢复结果。

## 4. 安全验收

### 必测泄露项

- IPv6 公网地址和 IPv6 DNS 泄露；
- 客户端绕过软路由访问外部 DNS；
- 代理核心停止时普通 WAN 直连；
- 未授权设备公网访问；
- 客户端之间横向访问；
- 客户访问管理员接口；
- 管理员跨租户、跨设备越权。

### 必测控制面项

- 重放、伪造和过期命令；
- 错投配置、版本降级和 fencing token；
- 设备证书轮换和吊销；
- OTA 签名、断电、失败回退和降级攻击；
- 日志、错误追踪、响应和诊断包中的敏感信息；
- 设备被标记风险后的凭证轮换、撤销和停止下发。

## 5. 稳定性验收

- 真实设备接入、随机 MAC、无浏览器设备和有线/无线混合。
- 主线路断开、恢复、短时抖动、备用线路故障和双线路同时故障。
- TCP、UDP、QUIC、TLS、DNS、长连接和持续上传。
- 云端断开、Agent 重连、设备重启和配置版本恢复。
- 连续 72 小时作为最低样机稳定性门槛；关键版本建议扩展到 168 小时。
- 稳定性期间不得出现未授权公网直连、配置版本丢失、频繁切线或不可解释的连接中断。

## 6. 指标使用原则

设计阶段只定义指标、采集方法、测试条件和失败判定，不填写未经实测的数值。最终销售验收指标必须按硬件型号、代理协议、线路类型、并发设备数和直播码率分别出报告。
