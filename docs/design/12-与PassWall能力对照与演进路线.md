# 与 PassWall 的能力对照与演进路线

> 状态：评估（2026-11-14）
> 目的：回答「这套系统是不是把 PassWall 的功能都具备了」，并把该补的排成顺序
> 参照对象：PassWall / PassWall2（OpenWrt 插件，Xray+sing-box 双内核）

## 0. 结论先说

**不具备，也不该照着做。** 两者是不同的东西：

- PassWall 是**给一台路由器用的本地插件**：人坐在 LuCI 界面前，导入订阅、选节点、点保存。
- LinkPilot 是**给一批设备用的运营系统**：云端下发签名配置、设备自动应用、失败回滚、门户给客户用。

功能上，PassWall 有 7 类能力我们缺（见 §2），其中 3 类属于「必须补」——尤其**探针测速**，它直接决定你承诺的「自动切线」能不能成立。另外 4 类属于「按产品定位不该照抄」，比如机场订阅导入。

## 1. 已经具备且做得更严的

| 能力 | PassWall | 我们 | 差异 |
|---|---|---|---|
| 透明代理 | iptables / nftables | nftables + 不变量校验 | 我们会在生成阶段拒绝「转发链被放开」「兜底拒绝被删」等半残配置 |
| 分流模式 | gfwlist / chnroute / 全局 / 直连 | `strict_global` / `cn_direct` / `direct_only` + 自定义规则 | 模式齐全，缺「一键切换」入口与远程规则订阅 |
| 每设备策略 | ACL 按 IP/MAC | 设备绑定 + RouteProfile + 锁线 | 我们的锁线按设备生效，不会连带同组其他设备 |
| DNS 防泄露 | DNS 劫持 + DoH | 强制 DNAT 劫持 + 阻断 DoT + 每线路 DoH | 一致 |
| IPv6 | 可开可关 | V1 强制全阻断 | 我们更严：不留「v6 裸奔」的中间态 |
| 配置生效 | 保存并应用，失败即断网 | 原子切换 + 摘要校验 + 失败回滚 + 版本拉黑 | 这是运营系统与本地插件的分水岭 |
| 凭证保护 | 明文存在 UCI | master key 密文 + 下发时 X25519 重封装 + AAD 绑设备与版本 | 我们从不落明文 |
| 审计 | 本地日志 | 云端审计 + 每次应用逐步结果 | 可追责 |

## 2. 缺的能力（按是否必须补排序）

### P0 必须补

| 缺口 | 为什么必须 |
|---|---|
| **探针与自动切线**（Phase 5 未实现） | 现在 `failoverPolicies` 只是数据模型。没有真实延迟/丢包探测，「主备切换」就是纸面功能，客户断线时你只能手动救。**已完成第一层：云端 TCP/TLS 握手测速（`control/probe.ts`），能筛掉死节点；自动切线仍需设备侧真实请求探测** |
| **规则集离线可用** | 现在 `geoip-cn` / `geosite-cn` 是远程 rule-set（`download_detour: direct`）。客户网断了或 GitHub 不可达，配置起不来就是全断。必须本地缓存 + 定期预热 |
| **模式切换入口** | 数据模型有 `strict_global / cn_direct / direct_only`，但门户和云端都没有「一键切换」按钮与二次确认 |
| **线路批量导入与测速** | 你现在是手工拉线路。没有批量导入 + 批量测速，线路一多就是纯人力 |

### P1 值得补

| 缺口 | 收益 | 风险 |
|---|---|---|
| 负载均衡（同线路组多节点按权重分摊） | 单条线路跑满时能摊带宽 | 出口 IP 会变，和「一人一 IP」冲突，只能用于共享型套餐 |
| Hysteria2 / TUIC | 弱网与高丢包下比 TCP 类协议好得多，直播上行敏感场景收益明显 | 新增协议面，需要更多真机验证 |
| 按时间规则（营业时间/夜间） | 客户侧自助限流 | 规则组合爆炸，先别做 |
| FakeDNS | 解决 App 硬编码 DNS、提升首包延迟 | **与「DNS 出口一致性」直接冲突**，我们卖的是出口干净，别为了快牺牲一致性 |

### P2 可选

- 服务器模式（把客户的机器变成出口节点）——等于做二级转售，涉及资质与合规，先不碰。
- 多租户计费打通。

### 明确不抄的

| PassWall 的能力 | 为什么不抄 |
|---|---|
| 机场订阅导入、节点二维码 | 你的线路是自己控的，订阅是给「买机场」的人用的，两套模型 |
| LuCI 界面随便改配置 | 和「配置单一来源」根本冲突：现场一改，云端就不知道设备真实状态 |
| 插件式升级 | 升级会覆盖用户配置，且无签名校验；我们走 OTA 双槽（设计 10 §4） |

## 3. 顺带修掉的一个硬伤（本轮已做）

查 tproxy 资料时确认：**只打 mark 不够**，内核还需要策略路由把 mark 指到 local 表，否则被 tproxy 标记的包不会被本机收下——表现为「规则全对，但流量黑洞」。

已在 `compiler/openwrt.ts` 的会话模式分支补上：

```sh
ip rule del fwmark 1 lookup 100 2>/dev/null || true
ip rule add fwmark 1 lookup 100
ip route replace local default dev lo table 100
sysctl -w net.ipv4.conf.all.route_localnet=1 >/dev/null 2>&1 || true
```

这一条如果漏了，真机上就是「登录成功、IP 没变、所有网站打不开」，而且日志里什么都不报——属于最难查的那类问题。

## 4. 演进顺序建议

```text
第一步（让闭环能验收）
  探针与自动切线 → 规则集本地缓存 → 模式切换入口 → 真机跑通登录闭环

第二步（让运营省人）
  线路批量导入 + 批量测速 → 崩溃与异常自动上报 → 配置漂移检测

第三步（让产品有差异）
  Hysteria2/TUIC → 负载均衡（仅共享型套餐）→ OTA 双槽灰度
```

## 5. 一句话回答「是不是都具备了」

透明代理、分流、DNS 防泄露、每设备策略、多协议这几项**结构和 PassWall 同级，个别地方更严**；但 PassWall 的「节点管理 + 测速 + 负载均衡 + 订阅」这套运营便利，我们**还没有**——其中测速和自动切线不是锦上添花，是你承诺「线路稳」的技术前提。
