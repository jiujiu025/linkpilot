# N100 + 外置 AP 系统基线与稳定性设计

> 状态：设计草案（2026-11-14），未在真机验证
> 替代关系：本文替代 `08-小米AX3000T-Board-Profile.md` 作为**当前交付基线**；08 保留为 ARM 一体机形态的历史资料
> 实物前提：主机为 Intel N100 小主机（**当前未装系统**），无线由外置 AP 提供，N100 只做网关

## 0. 一句话结论

系统选 **OpenWrt x86_64（squashfs 只读根 + overlay）**，磁盘按 A/B 双槽规划，启动失败靠 boot counter 自动回滚。
稳定性不靠"不出错"，靠"出错了 30 分钟内能自己站起来，或者被远程救回来"。

## 1. 稳定性的定义与指标

先定义清楚，否则验收无从谈起。

| 故障 | 目标行为 | 验收指标 |
|---|---|---|
| 客户现场断电/拔插头 | 来电自启，恢复到断电前最后一次可用配置 | 连续 20 次，20 次成功 |
| 升级过程中断电 | 自动回退到旧槽，业务中断 < 3 分钟 | 写槽中途拔电 5 次，5 次回退 |
| Agent 进程崩溃 | 自动重启，本地转发不中断 | `kill -9` 后 10 秒内恢复 |
| 系统整体卡死 | 硬件看门狗复位，复位后自愈 | 人为制造死锁，5 分钟内复位 |
| overlay 写满 / 损坏 | 告警，不宕机；可一键重建 | 写满后仍能转发与登录门户 |
| 网口丢包 | 72 小时零掉链 | i226 灌流测试，关闭 EEE/ASPM 前后对比 |
| 客户误操作恢复出厂 | 恢复出厂但**保留设备身份**，能重新上线 | 恢复后 5 分钟内自动重连云端 |

最后一条最容易漏：**恢复出厂必须保留身份分区**，否则设备在客户现场变成一块砖——你没法上门，也没法注册。

## 2. 系统选型

### 2.1 结论

**OpenWrt x86_64 官方镜像（squashfs 只读根 + overlay 可写层）。**

理由按重要性排：

1. **根文件系统只读**。squashfs 保证任何误改、断电、写坏，坏的最多是 overlay；根永远能起来。这是"不可砖"的地基。
2. **和现有代码零阻抗**。`compiler/openwrt.ts` 生成的就是 UCI，`supervisor.ts` 已按 procd 分支实现，`hardware.ts` 已识别 x86。换 Debian 等于把 `compiler` 的网络层重写一遍。
3. **恢复出厂是一等公民**。删 overlay 内容即可回基线，不需要重装系统。
4. **内存占用**是 Debian 的 1/4，N100 那点内存留给 sing-box 做加密和缓冲更划算。

### 2.2 为什么不用另外两个

| 方案 | 否决原因 |
|---|---|
| Debian/Ubuntu + nftables + sing-box | 全可写根。一次 `apt upgrade` 或一次断电就可能起不来；要做"不可砖"得自己造只读根 + A/B + 回滚，工作量比重写还大。客户现场没有显示器，起不来就是砖。 |
| PVE + OpenWrt 虚拟机 | 多一层虚拟化 = 多一个故障域，而且是最难排查的那层。快照回滚的收益，用 A/B 分区能拿到九成，代价小得多。 |
| ImmortalWrt / 第三方分支 | 内核与软件源更新更激进，出问题没人兜。量产设备要的是"三年不变"，选主线稳定版。 |

保留可迁移性：`hardware.ts` 已有 `initSystem` 抽象。若将来真要换 Debian，替换 network backend 即可，业务层不动。

### 2.3 版本策略

- 锁定一个 OpenWrt 稳定分支（当前 23.05.x），**量产机不跟随小版本升级**。
- 内核版本决定 i226-V 网卡驱动（igc）行为，升级内核必须重跑 §9 验收。
- 软件源改为自建镜像，断网也能装依赖；客户机器不允许直连上游源做 `opkg upgrade`。

## 3. 磁盘布局

单块 SSD（≥32GB，推荐 64GB 工业级/带掉电保护）。**分区一次规划到位，A/B 的实现在 V2 补，但空间先留出来。**

```text
p1  512MB   ESP / BIOS boot（UEFI 启动，GRUB）
p2  2GB     槽 A：kernel + squashfs 根
p3  2GB     槽 B：kernel + squashfs 根（V1 空置，V2 启用）
p4  512MB   身份分区：deviceId、设备私钥、注册凭据（独立，不随 overlay 恢复出厂）
p5  剩余    数据分区：overlay（配置）、配置快照、审计摘要、崩溃日志
```

为什么身份单独一个分区：

- 恢复出厂只清 overlay，不动 p4 → 设备仍然"是它自己"，能自动重连云端。
- 私钥不与配置同生共死，避免"恢复出厂 = 设备失联"。
- p4 挂载点 `/persist`，只读挂载给 agent 读，写入走一次性 `lp-identity` 工具。

## 4. 启动与回滚

### 4.1 boot counter 状态机

GRUB 环境块（双份写，防写坏）保存三个变量：`slot`、`try`、`ok`。

```text
正常启动：slot=A, ok=1                    → 直接进 A
升级写槽：写 B（sha256 校验 + sync）→ slot=B, try=1, ok=0 → 重启
启动后自检（60 秒内必须全过）：
   agent 起来了 / nft 规则加载了 / sing-box 活着 / 云端可连
   ├─ 全过 → ok=1，升级完成
   └─ 任一失败或 60 秒超时 → 重启，try 自增
try 超过 2 次 → 无条件回 slot=A
```

关键点：**回滚判定不能依赖 agent 自己上报**（agent 挂了就没法上报）。判定放在启动脚本里，agent 只负责"写一个 ok 标记文件"；启动脚本看到标记就置 `ok=1`，看不到就自增 try。

### 4.2 last-known-good 冷启动（堵裸奔窗口）

现有设计的顺序是：开机 → agent 起 → 连云端 → 拿配置 → 编译 → 应用。
这段窗口里设备是**没有防火墙规则的空壳**——WAN 已通、LAN 已通、没有任何拦截。

修法：把每次成功 apply 的产物（`nftables.nft` + `singbox.json` + `leases.json`）在 `/persist/last-good/` 留一份，开机时由 init 脚本**在拉起 network 之前**先加载：

```text
开机 → 加载 /persist/last-good/nftables.nft（默认拒绝立刻生效）
     → 启动 network / dnsmasq
     → 启动 sing-box（用 last-good 配置）
     → 启动 agent → 连云端 → 有更新才编译应用
```

这样断电重启后，客户家里的网络在 20 秒内恢复到断电前状态，且全程没有裸奔窗口。
这也是"云端断线本地继续工作"能真正成立的物理基础。

## 5. BIOS / 固件基线（N100 真正的坑在这里）

| 设置项 | 值 | 为什么 |
|---|---|---|
| Restore on AC Power Loss | **Power On** | 客户现场断电后来电必须自启，否则要派人上门按电源键 |
| Secure Boot | **Disabled** | OpenWrt 镜像无签名，开机直接拒绝启动 |
| ASPM / PCIe 节能 | **Disabled** | i226-V 在 ASPM 下会不定时掉链、丢包，是"网络莫名断了"最常见的根因 |
| 深度 C-state（C6/C7/C8） | **限制到 C1/C3** | 同上，且会让定时器抖动、隧道易断 |
| Intel SpeedStep / 睿频 | 保持开启 | 关掉会让小包性能掉一半；功耗不是瓶颈 |
| 内存频率 | **关闭 XMP/EXPO**，跑 JEDEC 保守频率 | 小主机散热差，内存不稳表现为随机重启 |
| 硬件看门狗 | **开启（iTCO_wdt）** | 系统死锁时的唯一自救手段 |
| 网络启动 / PXE | **关闭并从启动项移除** | 插上网线后误进 PXE，等于设备失联 |
| 启动顺序 | 固定 p1 优先，USB 靠后 | 防止插 U 盘就改启动目标 |
| 来电快速启动 / Fast Boot | 关闭 | 会跳过部分设备初始化，网卡偶发不识别 |

另外两条运行期设置（不是 BIOS，但要写进基线脚本）：

- `ethtool --set-eee <if> eee off`：即使 BIOS 关了 ASPM，EEP 仍可能在驱动层打开，双保险。
- 定时 `sync` + overlay 写入节流：廉价 SSD 最怕高频小写。

## 6. 网口命名与角色固化

这是远程设备最经典的翻车点：换一块主板、刷一次固件，`eth0`/`eth1` 顺序变了，WAN 和 LAN 对调，设备直接失联。

设计：

1. **按 PCI 路径绑定名字**，不按探测顺序。生成 `/etc/udev/rules.d/70-linkpilot-nic.rules`，用 `ID_PATH` 匹配，命名 `wan0`、`lan1`、`lan2`……
2. **首次开局自动判角色**：四个口里，哪个口检测到 DHCP offer / PPPoE PADO / 上游 ARP，就定为 WAN；其余为 LAN。判定结果写进配置并固化，之后不再自动变。
3. **接口指纹上报**：把 `(PCI 路径, MAC, 当前名, 角色)` 上报云端存一份。设备换机或误刷后，云端能一眼看出"这台的口序和登记的不一致"。
4. UCI 侧必须**显式生成 device/bridge 段**。ARM 一体机靠设备树固化，x86 不会——这是本次代码要补的缺口（见 §11）。

## 7. 运行时不变量

| 不变量 | 做法 | 违反后果 |
|---|---|---|
| 根文件系统只读 | squashfs，配置只写 overlay | 误改/断电污染根，设备起不来 |
| 日志不落盘（大流量场景） | `/var/log` 挂 tmpfs，只把审计摘要与崩溃前 200 行写 p5 | 廉价 SSD 写坏，1 年内返修 |
| 配置单一来源 | 所有 `/etc/config` 由编译器生成，手工改动下次 apply 被覆盖 | 现场排障改动被静默回滚，人机互坑 |
| 漂移检测（只报不改） | 每 10 分钟比对关键配置哈希 vs 期望哈希，不一致上报 | 现场手工改动无人知晓 |
| 时间可信 | RTC + NTP + 单调时钟三保险；时间跳变 > 5 分钟告警 | 签名/nonce/TLS 全部依赖时间，时间错=全线鉴权失败 |
| 配置快照 | 每次成功 apply 后 `/etc/config` 打包，保留最近 5 份 | 无法快速回到"昨天还好好的"状态 |

漂移检测"只报不改"是有意的：现场工程师可能在排障时手工改过，自动覆盖会让人以为设备在抽风。

## 8. 远程可达与自助恢复

设备在客户家里，你去不了。可达性要设计成三层：

1. **主通道**：agent 出站长连接（现有设计），断线自动重连 + 指数退避。
2. **备用通道**：独立 WireGuard 回连（与 agent 通道不同实现、不同端口），仅运维侧可用。可选加 4G USB dongle 做带外——成本自己权衡，但主宽带断了的工单不罕见。
3. **自助兜底**：客户按 reset 键 3 次（3 秒内）→ 恢复出厂配置但**保留 p4 身份分区** → 设备重新注册上线，配置由云端重新下发。

第 3 条的价值：绝大多数"设备坏了"其实是配置被搞乱，客户自己能一键恢复，你就少一趟上门。

## 10. 分期落地

| 阶段 | 内容 | 目的 |
|---|---|---|
| V1 能交付 | 单槽 + 只读根 + last-good 冷启动 + 断电自启 + 接口指纹 + 身份分区 + 恢复出厂保身份 | 客户能拿到能用的机器，出事能自救 |

## 13. 与 AX3000T 形态的差异（会咬人的两条）

1. **客户端隔离失效**：原来靠网关 nftables 兜底"客户端之间禁止互访"。现在无线客户端互访走 AP 的二层交换，不经过 N100，nft 拦不到。必须在 AP 上开 isolation，或按 SSID 分 VLAN 由网关做三层隔离。`compiler/nftables.ts` 里那条 `iifname br-lan oifname br-lan reject` 只对**经网关转发的**流量有效，同网段二层流量它看不见。
2. **DHCP 归属唯一**：source-IP 分流依赖 N100 做 DHCP。AP 必须是桥接/dumb AP 模式、关掉自己的 DHCP，否则会出现两个 DHCP 服务器，客户端随机拿到不归 N100 管的地址，分流直接失效。

## 14. AP 侧配置基线（AP 只做二层）

结论：**AP 只发射信号（桥接/AP 模式）是正确形态，也是唯一推荐形态。** 但"只发信号"意味着三样东西从网关手里交出去了，必须在配置和产品口径上补回来。

### 14.1 必做设置

| 项 | 要求 | 不这么做的后果 |
|---|---|---|
| 工作模式 | AP / 桥接，关闭路由与 NAT | 双重 NAT，客户侧无法从云端看真实源 IP，分流与审计全乱 |
| DHCP 服务 | **关闭** | 两个 DHCP，客户端随机拿到非 N100 地址，源 IP 分流失效 |
| 上行接入口 | AP 的 **LAN 口**，不是 WAN 口 | 接 WAN 口会走 AP 自己的路由/NAT |
| 管理地址 | 同网段固定 IP，且放在 DHCP 池之外 | 与租约冲突，AP 后台失联 |
| 客户端隔离 | **关闭**（当前产品要求同网段互访，见 11 号文档 §13） | 开启会导致互访直接不通；代价是未登录设备与已登录设备在二层也不隔离 |
| 自带"访客网络" | 关闭 | 访客网络自带 NAT 与独立 DHCP，绕过网关全部策略 |
| 中继 / Repeater / Mesh 无线回程 | 禁止 | 多一跳 NAT、吞吐腰斩、源 IP 不可控 |
| 自动升级 / 厂商云管理 | 关闭 | 半夜自己重启改配置，等于埋一颗定时雷 |
| 信道与功率 | **固定**，不选 Auto | Auto 会在 DFS 信道间跳，直播直接断流 |
| 频宽 | 2.4G 20MHz，5G ≤80MHz | 160MHz 抗干扰极差，稳定性换速度不划算 |
| 802.11k/v/r | 多 AP 场景开启 | 单 AP 无所谓；多 AP 无漫游会粘信道 |

### 14.2 客户端隔离的三种做法

| 方案 | 条件 | 代价 |
|---|---|---|
| A. AP 开 isolation | AP 支持 | **全有或全无**：投屏、局域网打印、NAS 互访一并断掉 |
| B. 每 SSID 一个 VLAN + N100 做 802.1Q 子接口 | AP 支持多 SSID + VLAN，且上联口能跑 trunk | 配置复杂，但能按网段精细放行；推荐给有内网互访需求的客户 |
| C. 不隔离，只拦未授权出网 | 无 | 放弃"客户端互访隔离"这条承诺，必须写进客户告知 |

注意 A 的硬限制：**AP 的隔离是二层的，无法按 IP 白名单放行**。客户既要隔离又要投屏，只能走 B。

### 14.3 交出去的三项能力怎么补

1. **Wi-Fi 口令**：门户里的"修改口令"在纯 AP 形态下无落点。当前处理是硬件无无线时不显示该按钮；后续要么接 AP 的管理 API，要么在门户改成"请在你的 AP 后台修改"的指引文案。**不要留一个点了没反应的按钮。**
2. **信道/功率调优**：网关看不到射频，客户抱怨卡顿时排查链多一跳。需要单独一份 AP 配置基线（见 14.1），并在验收清单里加一项"AP 信道是否固定"。
3. **客户端隔离**：位置从网关搬到 AP，见 14.2。`compiler/nftables.ts` 里那条 br-lan→br-lan 的 reject 保留，它对**经网关转发**的流量仍然有效（例如 VLAN 方案下的跨网段），但对同网段二层无效，不能当成隔离已生效的证据。

## 15. AP 候选：京东云雅典娜 AX6600（RE-CS-02）

### 15.1 硬件本身够用

| 项 | 规格 | 评价 |
|---|---|---|
| SoC | 高通 IPQ6010，四核 A53 1.8GHz + 1.5GHz NPU | 做纯 AP 富余 |
| 内存 | 1GB DDR4 | 够 |
| 无线 | 三频 WiFi6：2.4G 574 / 5.2G 4804 / 5.8G 1201，支持 160MHz | 三频是优势：可给直播单独留一个频段 |
| 网口 | 1×2.5G（官方固件偏 WAN）+ 4×1G LAN + USB3.0 | 2.5G 回程需刷机才能改 LAN |
| 存储 | 64 / 128 / 256G eMMC | 与 AP 角色无关，是 PCDN 缓存 |
| 官方宣称带机量 | 253 台 | 纯 AP 场景远超需求 |

硬件不是问题。问题是它是**路由器 + PCDN 节点二合一**，出厂定位就不是"老实发个信号"。

### 15.2 三个必须先解决的问题

1. **边缘计算残留（最硬的一条）**
   官方 App 有四种积分模式：极限积分 / 积分优先 / 智能加速 / 上网优先。最温和的"上网优先"也只是把边缘计算上行限到 10Mbps 左右——**仍然在上传**；而"极限积分"反而会关闭 WiFi，方向是反的。
   也就是说：**官方固件里没有一个状态叫"纯 AP、不跑 PCDN"**。你无法向客户证明这台机器没有在偷偷上传。

2. **"三件套"核对：2/3，缺的正好是安全那条**

   官方固件（JDCOS）的实际能力，按官方"如何设置 AP 模式"教程核对：

   | 需求 | 官方固件 | 说明 |
   |---|---|---|
   | 桥接 / 纯 AP | ✅ 有 | Web 后台 → 路由设置 → 上网设置 → **工作模式切换** → 有线 AP 模式（扩展有线网络）。前提是先以任意上网方式联网成功；拨号中或 Mesh 状态下不能切 |
   | 关 LAN 侧 DHCP | ✅ 等效有 | AP 模式下设备无路由功能，DHCP 由上级（N100）承担 |
   | 主 SSID 客户端隔离 | ❌ **没有** | 官方功能清单只有：访客网络、防蹭网（按设备禁网/限速）、上线提醒、重启计划、软件升级、隐藏 SSID。没有 AP isolation 开关 |

   更麻烦的是：**切到 AP 模式后，访客网络和 Mesh 都会被禁用**（官方弹窗明示"将无法使用路由器高级功能、访客WiFi、Mesh模式"）。所以想借"访客 SSID"来获得隔离这条路也堵死了。

   注意别把"防蹭网"当成隔离：黑名单是**针对某个设备禁止出网**，不是阻止客户端之间互访。两台手机互 ping，在官方固件的 AP 模式下预期是通的。

   结论：§14.2 的方案 A（AP isolation）和方案 B（多 SSID + VLAN）在官方固件上**都不可用**，只剩方案 C（不隔离），而这与门户里"未授权设备无法出网 / 客户端互访受控"的表述冲突。

3. **云控与自动升级**
   JDCOS 由京东云后台管理，固件升级、插件下发都不在你手里。交付设备最怕的就是半夜自己重启改配置——恰好踩中 §5 基线里"关闭自动升级"这条。

### 15.3 更要紧的是业务冲突，不是技术问题

这台机器的默认工作就是**占用上行带宽跑 CDN 分发**。而我们的卖点是「原生独享 IP、不超售、直播稳定」：

- 上行被边缘计算抢走 → 客户直播推流直接掉帧、卡顿，而你会被叫去排查"是不是你们线路不行"。
- 大量外联连接 + 长期上传 → 出口 IP 在平台侧的风控画像变差，和你卖的"干净住宅/机房 IP"完全相反。
- 运营商侧风险：2024 年以来多地对无线宝类 PCDN 设备限速、要求签承诺书，2026 年起无相关资质从事 PCDN 还存在合规争议。你的业务本身在资质链条上（橙汁持证、百万拳代理），这类设备出现在客户侧，解释成本极高。

一句话：**客户侧跑着 PCDN，你就没法解释"为什么卡"。**

### 15.4 两条路

**A. 自用 / 临时验证（可接受，前提是接受"客户端互访不隔离"）**

1. App 里退出积分插件、关闭边缘计算，模式切"上网优先"并把上行限值压到最低；
2. 按官方路径切有线 AP 模式（路由设置 → 上网设置 → 工作模式切换），切换前先关 IPv6；
3. 实测三件事：终端默认网关是否为 N100（确认没有第二台 DHCP）、连续 72h 上行有无异常外联、两台终端互 ping 是否 **通**（预期通，用于确认"确实没有隔离"，不是配置失败）。

能过就用它自测，但**别拿它交付**——尤其别给有"设备互访要隔离"要求的客户。

**B. 交付（两个选择）**

- **B1 刷 OpenWrt**：该机型属 IPQ6018 家族（代号 cs-02），需经 9008/U-Boot 刷入并按 GPT 重排分区，把带 PCDN 的分区抹掉；刷后 2.5G 口可改为 LAN，hostapd 可配 `isolate=1`、多 SSID 与 VLAN——三件套这才齐全。代价是自建固件维护与返修预案，且 ath11k 无线的长期稳定性要自己压测。
- **B2 换商用 AP**（TP-LINK 商用 / UniFi / H3C 小贝）：纯 AP 模式 + isolation 开关 + 多 SSID + VLAN + 可关云控，出厂即具备，三年不用你管固件。

### 15.5 结论

- 雅典娜 + 官方固件：**桥接和 DHCP 都合格，客户端隔离无解**。只能做"不隔离的 AP"。
- 当**自测 AP**：可以，先把积分关干净，并把"互访不隔离"当成已知条件。
- 当**交付件**：不建议，除非走 B1 刷 OpenWrt 并愿意承担固件维护。
- 量产选 AP 的第一条门槛不是 Wi-Fi 速率，而是**"能不能把它自己的所有智能功能关掉，同时把隔离开关给你"**。参数漂亮的消费级 PCDN 机型，恰恰最难过这一关。
