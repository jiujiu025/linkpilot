# Phase 0 审查结论与开发 Task List

## 1. 当前状态

### 已确认

- 采用单 SSID 和本地统一登录门户。
- 客户用户与设备管理员使用同一登录入口，由权限返回功能。
- 设备管理员只管理绑定的单台软路由。
- 云端运营后台管理设备、客户、线路、策略、探针、部署和审计。
- 云端通过 Router Agent 主动出站连接，不进入实时转发路径。
- 支持直播设备远程授权、设备级线路绑定、主备线路和本地持续运行。
- 采用 sing-box 优先、Xray 兼容、WireGuard 独立管理的执行器结构。
- V1 默认关闭 IPv6，DNS 强制接管，Kill Switch 默认拒绝。
- 配置采用 Desired/Observed State、版本、签名、健康验证和自动回滚。
- 首款目标样机为小米 AX3000T，最低档参考 MT7981B 双核 1.3GHz、256MB 内存、128MB Flash、Wi-Fi 6、4 个千兆网口；必须确认具体硬件版本后，在真实设备上验证；N100/x86 仅作为后续性能对照平台。

### 实际未实现

- OpenWrt 定制固件和本地门户；
- Router Agent、本地 Helper 和探针；
- sing-box/Xray/WireGuard 适配器；
- 策略编译器、DNS 防泄露和 Kill Switch；
- 云端 API、数据库、Worker、权限和审计；
- 配置部署、回滚、证书管理和 OTA；
- 真实线路、硬件、直播和安全测试。

- 本地数据面与门户设计；
- 策略、防泄露与线路切换设计；

## 3. 分阶段开发 Task List

### Phase 0：架构、小米 AX3000T 样机和基线确认

**目标**：完成设计评审、锁定小米 AX3000T 的具体硬件版本、真实线路和测试设备。

**计划文件**：

- `docs/design/` 全部架构文档；
- `docs/design/08-小米AX3000T-Board-Profile.md`；
- `docs/design/09-AX3000T-备份恢复与真实性能测试计划.md`；
- `docs/test/硬件与线路测试计划.md`；
- `docs/security/威胁模型.md`；
- `docs/adr/` 关键架构决策记录。

**数据库变化**：无生产数据库；只定义实体、约束和迁移原则。

**API 变化**：无生产 API；冻结接口边界、错误模型、鉴权模型和版本策略。

**测试**：小米 AX3000T 硬件档案、只读原厂备份方案、恢复/救砖路径、真实线路清单、直播设备清单、协议能力测试矩阵和泄露测试方案。

**验收**：确认小米 AX3000T 的完整型号/硬件版本、分区和启动方式、恢复路径、基础版资源预算、首批协议、首批真实线路、性能采集方法和 Phase 1 范围。

### Phase 1：软路由基础数据面

**目标**：单 SSID、DHCP、门户、基础隔离、IPv6 默认关闭、本地状态页。

**计划文件**：OpenWrt 镜像工程、网络配置模板、本地门户工程、基础集成测试。

**数据库变化**：建立设备本地状态和云端最小设备登记表；不引入线路凭证业务。

**API 变化**：本地门户登录、会话、设备发现和健康摘要接口；暂不开放复杂线路管理。

**测试**：真实手机、电脑、编码器、摄像机接入；未认证设备隔离；HTTP 门户引导；不劫持 HTTPS。

**验收**：终端获得 IP、能访问门户；未认证终端不能访问公网和其他客户设备；IPv6 默认关闭并通过实测。

### Phase 2：账号、权限和设备授权

**目标**：统一登录、客户/设备管理员分权、待授权设备和设备级绑定。

**计划文件**：身份模块、权限策略、DeviceSession、DiscoveredClient、DeviceRouteBinding 模块及测试。

**数据库变化**：Organization、User、Role、Session、RouterDevice、DeviceSession、DiscoveredClient、Binding。

**API 变化**：门户登录、待授权设备、绑定、撤销和强制下线；增加租户和资源归属校验。

**测试**：同 SSID 多账号、多设备、随机 MAC、二次 NAT、过期绑定、并发绑定和越权。

**验收**：客户只能访问自身资源；设备管理员只能管理单台绑定设备；无浏览器设备可被授权并保持隔离边界。

### Phase 3：代理、分流和防泄露

**目标**：sing-box、必要 Xray Adapter、WireGuard、RouteProfile、DNS、IPv6 防护和 Kill Switch。

**计划文件**：策略编译器、执行器适配器、nftables/policy routing 模板、DNS 服务和真实线路配置导入器。

**数据库变化**：Provider、CustomLine、ProtocolProfile、LineGroup、RouteProfile、RoutingRule、FailoverPolicy、凭证引用。

**API 变化**：线路和策略管理、设备线路绑定、手动切线；敏感字段只允许受保护管理接口短暂写入。

**测试**：真实 VLESS/Trojan/Shadowsocks/WireGuard、TCP/UDP/QUIC、DNS/IPv6/直连泄露、核心停止和规则冲突。

**验收**：严格全局代理、大陆直连/其他代理和白名单行为符合规则；代理异常时没有普通 WAN 直连。

### Phase 4：Router Agent 和云端控制面

**目标**：设备激活、出站加密通道、固定命令、Desired/Observed State、部署、验证和回滚。

**计划文件**：Agent 工程、本地 Helper、云端 API/Worker、配置编译服务、部署状态机和审计模块。

**数据库变化**：DeviceIdentity、DeviceCredential、DesiredState、ObservedState、ConfigRevision、Deployment、Command、Outbox。

**API 变化**：Agent enrollment、heartbeat、desired-state、observed-state、command ack；所有消息独立鉴权和幂等。

**测试**：断线重连、过期命令、重放、错投版本、签名失败、配置失败回滚和云端不可用。

**验收**：云端不能执行任意 Shell；配置失败自动恢复上一稳定版本；云端断开时本地配置和自动切线继续运行。

### Phase 5：探针、诊断和自动切线

**目标**：本地/云端探针、健康状态机、主备切换、冷却、锁和切换审计。

**计划文件**：Probe、Incident、Alert、Failover 状态机、诊断树、限速测速任务和事件聚合。

**数据库变化**：Probe、ProbeCheck、HealthSnapshot、Incident、Alert、切线事件和任务执行记录。

**API 变化**：诊断、探针历史、事件、手动切线、手动锁线和维护模式接口。

**测试**：真实断线、抖动、恢复、双故障、长连接、直播上传、探针限速和切线竞态。

**验收**：故障判定可解释；不因短暂抖动频繁切线；新连接可切换；已有直播连接中断风险有明确记录。

### Phase 6：品牌化门户、运营后台和模拟视图

**目标**：完成正式客户门户、单设备管理员页面、运营后台和默认只读模拟客户门户。

**计划文件**：本地 UI、云端 UI、BFF/权限策略、impersonation 模块、可访问性和响应式测试。

**数据库变化**：ImpersonationSession、操作确认、UI 审计和后台资源范围。

**API 变化**：后台资源查询、诊断、授权、部署、线路、审计和模拟会话接口。

**测试**：角色矩阵、跨租户测试、敏感字段扫描、模拟会话过期和写操作二次确认。

**验收**：客户看不到底层系统和线路凭证；管理员可诊断指定设备；模拟会话显示明显运维状态并全量审计。

### Phase 7：OTA、量产和恢复

**目标**：签名固件、双分区 OTA、失败恢复、证书轮换、激活和售后诊断包。

**计划文件**：固件构建、签名发布、OTA Worker、设备升级状态机、恢复脚本和量产文档。

**数据库变化**：FirmwareArtifact、Release、DeviceUpgrade、CertificateRotation、RecoveryEvent。

**API 变化**：发布、分批升级、设备升级状态、暂停、回退和恢复报告接口。

**测试**：真实设备升级、断电、空间不足、签名失败、版本降级、双分区回退和救砖。

**验收**：目标硬件至少完成一次成功升级和一次失败回退；证书、配置和审计数据符合设计；形成量产验收报告。

## 4. 未决问题

以下问题需要在 Phase 0 设计评审中确认，当前不应通过编码自行假设：

1. 小米 AX3000T 的完整型号、硬件版本、SoC、RAM、Flash、无线芯片、交换芯片、分区表、启动方式和恢复方式。
2. 首批真实线路的协议、地区、出口要求、授权方式和合规边界。
3. 本地门户认证是完全本地账号，还是云端账号的缓存/联机混合模式。
4. 无浏览器设备的默认授权有效期、最大设备数和撤销策略。
5. 首批必须支持的协议是否限定为 VLESS、Trojan、Shadowsocks、WireGuard。
6. 云端部署环境、数据库、缓存、消息队列和密钥管理系统的选型。
7. 是否需要支持多 WAN 物理线路，还是 V1 只支持多代理出口。
8. 目标直播平台、码率、并发直播数量和可接受中断时间。
9. OTA 是否要求生产级双分区，还是先以样机可恢复升级验证为目标。
10. 客户门户和云端后台的品牌域名、证书和运营租户模型。

## 5. 下一阶段建议

在用户确认前，建议只做三项准备性工作：

1. 评审 `docs/design/` 文档并冻结架构决策。
2. 准备一台可确认硬件版本的小米 AX3000T，按只读流程建立原厂固件备份和救砖路径；本阶段不刷机、不恢复出厂、不覆盖固件。
3. 按测试计划准备真实线路、直播设备、温度/资源采集方式和泄露测试环境。
4. 建立 Phase 0 的 ADR、威胁模型和测试记录模板。

确认后再进入 Phase 1；Phase 1 首批只实现基础数据面和本地门户，不提前实现大规模后台、复杂协议和高级 SD-WAN。
